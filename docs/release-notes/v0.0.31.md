# v0.0.31 — 少打断、原任务接着做

> Fewer interruptions, finish the original task.

## 修复与改进

- **“等你处理”和“你主动接管”不再混淆**：等待人工处理时保留原任务，不再误显示成“已结束”，并显示等待原因和继续入口。
- **聊天能分清“没有活动授权”和“任务仍保留”**：新增只读字段 `taskRetained`、`taskState`、`continuationState`、`continuationFailure`；原 `taskPresent` 仍只查询当前授权编号。这些状态不会赋予操作权限，也不包含任务标识或页面文本。
- **继续失败后能再次确认**：尚未尝试唤醒聊天，且没有恢复授权或已确认撤销本次授权时，显示 `NOT_RESUMED` 和真实技术原因。原任务、历史和会话保持不变；处理原因后可再次确认继续，不必重说任务、重新配对或重设范围。
- **“已恢复，但聊天提醒未确认”单独处理**：`FAILED` 保守表示这次唤醒结果未确认，不重复投递同一次唤醒，也不会仅凭“当前没有授权”就允许重试。如果授权已恢复，仍可回聊天发起新的读取，无需再次授权。
- **必要的停手保护保留**：锁屏、断线、敏感确认和结果不确定时仍停手，不自动重连或恢复，也不重放已发送或结果不确定的操作。继续只对同一运行环境和会话有效；App 或进程重启不会自动恢复旧任务。
- **继续按钮首屏可见**：浮窗的继续入口不会再被通知和最近记录挤到下面；未恢复时先显示原因和“再次确认继续”，不重复要求完成旧人工步骤。浮窗仍只打开原生确认，确认后才恢复授权；正在恢复时，停手按钮仍优先可见。
- **减少无谓的人工接管引导**：普通加载、窗口切换和暂时读不到稳定页面时，应保留有效的原任务，并有限地重新读屏；普通聊天提问、表单和 OpenCode 权限回复不等于手机交接。真正需要在手机上手动处理的步骤仍使用受保护的接力流程。未新增控制动作、请求参数或权限；工具说明和文案测试不能保证所有真实模型都不再误中断。

## Fixes and improvements

- **`NeedUser` is separate from a person `TakenOver`**: an agent request for a person is no longer shown as “you took over”. A retained native task is not labelled Ended merely because a needs-check record exists; while waiting, the original task, the waiting reason and its Continue entry remain visible.
- **Read-only handoff status**: `taskPresent` remains the strict live-epoch boolean; `taskRetained`, `taskState`, `continuationState` and `continuationFailure` come from the same bound task store and screen facts. They grant nothing, resume nothing, and expose no task key or page text.
- **A technical failure before recovery can be confirmed again**: a continuation that fails before native readiness and before any wake, with no new grant (or a confirmed exact rollback), records `NOT_RESUMED` with a fixed reason. The same task key, history, latest attempted epoch and native stop receipt are kept. The task is not abandoned; a person may confirm again and enter a fresh grant/Observe without retelling the task, reconfiguring the scope or resetting it.
- **`Failed` stays conservative and the same wake is never re-sent**: only a real recovery that reached the chat wake can become `FAILED`, meaning that one wake was not confirmed. That same wake is not retried automatically or manually, and a missing grant alone never turns an old `Failed` into a retry. If recovery is established and only the wake failed, the grant stays active; an explicit read-only read in the chat does not require another authorization.
- **Hard stops and boundaries are unchanged**: unknown outcomes, a newer owner, screen lock, connection loss and sensitive confirmation remain hard stops. There is no automatic scope recovery, reconnect or replay of sent results. An original task is valid only for the same runtime/session; an App or process restart never restores an old task automatically.
- **The UI entry is direct**: the primary CTA stays visible on the first screen and is not pushed out by chat notices/Recent. `NOT_RESUMED` shows the fixed technical cause and Confirm again instead of repeating the old manual step. Overlay Continue still only navigates to the native confirmation dialog; a grant appears only after the person confirms, and no overlay authorization was added. Stop controls stay ahead of `SENDING`/`DELIVERED`/`FAILED`.
- **Guidance covers only confirmed handoffs**: ordinary busy/window/stale states get a bounded fresh read-only observation on the same live grant and never become an automatic `need_user`. A handoff is for genuine manual phone work such as login, captcha, payment, phone permission or unsupported input. Ordinary chat questions, forms and OpenCode permission replies do not need a phone handoff. No tool input action or schema was added; a SENT/UNKNOWN mutation is never replayed. Guidance/copy tests are not real-model compliance and cannot guarantee that every automatic interruption is eliminated.

## Verification and limitations

- **Real API 35 / x86_64 independent debug App + synthetic fixture**: the old v30 baseline reproduced the false status, the retained task shown as Ended/You took over, and the no-op continue button. The new build reports `taskRetained=true` / `WAITING_USER` / `NO_GRANT` while waiting and keeps the original task.
- **First continue under 30-second busy**: it returned `NOT_RESUMED` + `SCREEN_NOT_IDLE` before any wake, sent no wake and kept the same task. After the page stabilized, a second person confirmation entered a fresh native epoch/route/Observe; the original session received exactly one fixed wake, the request tool count stayed at the original task's one, one tap was made, and an independent read-back saw `Saved` exactly 1. The final-layout source APK repeated the same negative-then-success run.
- **Ordinary running busy snapshot**: it returned `HIERARCHY_NOT_IDLE` while phase stayed `READY`, the epoch/grant stayed the same, the connection stayed connected and unblocked, and the task stayed `ACTIVE`; no `need_user` was created. A fresh snapshot after the page stabilized succeeded on the same epoch without another native confirmation. This shows native behavior, not a guarantee that a real model follows the description.
- **Second manual stop and wake fault**: a second manual stop reset the previous `DELIVERED` state to `IDLE`. After native recovery, an isolated wake HTTP fault produced `FAILED`, but phase stayed `READY`/`ACTIVE`, connected and unblocked; the original session's fixed-wake count was before 1 / after 1 and the fault rule was cleaned up. An explicit read-only chat snapshot needed no new authorization and stayed on the same grant; `FAILED` remained non-retryable. Explicit model finish reached `ENDED_PENDING_CHECK`, and native Close set `taskRetained=false`.
- **Pre-release full checks**: 2,070 JVM tests with no failures, errors or skips; 361 Node tests (360 passed plus one existing skip); 72 Python tests; Android lint, debug and AndroidTest APK packaging passed with retained warnings/information, not a zero-warning claim. The final description copy was rechecked with all 361 Node tests and an APK asset build.
- **Evidence limits**: no new device instrumentation, no physical device, no API 37/arm64, large-font, landscape or TalkBack coverage. The new layout has visual evidence only for the default English current-phone viewport; earlier evidence is not expanded. Dynamic hierarchy remains unsupported and Unicode input limits are unchanged. The production App was not touched; test tasks, permissions, AppOps, overlay mode, wireless debugging, owned forwards, fixture wrapper, model server, inspector and fault were all restored/cleaned.
