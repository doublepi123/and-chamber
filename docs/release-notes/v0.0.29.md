## 修复与改进

- **修复“原生显示 Ready，但新 request 返回 STANDING_BLOCKED”**：此前 UI 没有把 core 的 standing pause 显示为真实暂停原因，runtime 重启后又可能既没有任务、也没有恢复入口。现在原生页显示实际的 **Paused** 原因，并提供“恢复聊天”；该恢复使用明确的人员确认框。既有 standing scope 与永久时限保持不变。
- **仅允许显式的人员无任务恢复**：只有在没有活动任务、授权、停止记录、在途操作或待核对的未知结果，且连接、tool 和前台 stop entry 都已就绪时，人员确认才可解除该暂停。确认本身不创建 grant、不启动应用、不发送 wake prompt、不重放旧操作，也不修改 scope deadline 或 session binding。打开原生页、重新连接或 RPC Ready 都不会自动清除 block；旧 halted task 继续保留原有 Continue，不会仅因 Paused 被禁用；未知结果仍需核对，scope 恢复不能绕过它。

## Fixes and improvements

- **Fixed “native Ready but a new request returns STANDING_BLOCKED”**: the UI previously did not surface the core standing pause as its real pause reason, and a runtime restart could leave neither a task nor a recovery entry. The native page now shows the actual **Paused** reason and offers **Resume chat** through an explicit person confirmation dialog. Existing standing scopes and permanent durations are unchanged.
- **Explicit person-confirmed no-task resume only**: the pause can be cleared only when there is no live task, authorization, stop record, in-flight operation or unresolved unknown result, and the connection, tool and foreground stop entry are ready. Confirmation does not create a grant, launch an app, send a wake prompt, replay an old action or change the scope deadline/session binding. Opening the native page, reconnecting or RPC readiness never clears the block automatically. An old halted task keeps its original Continue path and is not disabled merely by Paused; unknown outcomes still require checking, and scope resume cannot bypass that check.

## Verification and limitations

- The real interaction was reproduced and verified with an independent test package on the **API 35 / x86_64 emulator**. Baseline: use the scope once, finish, Stop/Start from Home, close the ended task, then Find and connect showed UI Ready while the status was `RUNTIME_CHANGED` and a fresh request returned `STANDING_BLOCKED`. After the fix the same path showed the real **Paused** state; Cancel kept the block, epoch and no-task state; Confirm became Ready, cleared the block, created no grant or task and left the epoch unchanged; the exact persisted standing config was unchanged; conversation context and model transcript counts stayed unchanged, confirming no prompt was sent. A subsequent fresh request ran normally, and tap/readback kept the Saved count at 1.
- The existing stopped-task **Continue beside the chat…** path also passed: after `need_user`, native confirmation sent exactly one continuation prompt, and the same session completed an input verified by independent read-back. Actual paused, confirmation and resumed-screen screenshots were reviewed as well.
- Pre-release full checks passed: 1,970 JVM tests with no failures, errors or skips; 359 Node tests (358 passed plus one existing skip); and 72 Python tests. Android lint, debug and AndroidTest APK packaging passed with existing lint warnings/information.
- This regression is covered only on the API 35 / x86_64 emulator. The model remains a deterministic protocol fixture, not real reasoning or autonomous planning. Tablet, vendor systems, TalkBack and multi-window differences are not covered, and no new device instrumentation was executed.
- The existing default-off and trusted-whole-local-runtime boundaries remain. This fix does not claim to eliminate every pause, unknown-outcome or vendor difference.
