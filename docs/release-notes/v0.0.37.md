# v0.0.37 — 读屏不再因为多带一个参数而报 HTTP 400

> A snapshot no longer fails with HTTP 400 because of one extra field.

## 修复

- **多带了参数就整个调用失败**：模型调用读屏（`snapshot`）时，常会把刚从状态里看到的 `epoch` 一起带上。以前手机工具把多出来的参数当成错误整个拒绝，模型只看到 “HTTP 400”，于是一直卡在读不了页面这一步。现在 `epoch`、`observationId` 这类从上一步抄过来的参数，用不到的动作会直接忽略，不再拒绝。
- **参数真错了也能看懂原因**：参数确实不对时，不再返回 HTTP 400，而是返回普通的错误结果 `INVALID_REQUEST`，并说明各个动作需要哪些参数，模型能据此改正后重试。什么操作都不会执行。

## 验证范围

- 在模拟器（API 35 / x86_64）上直接调用真实的手机工具接口：带 `epoch` 的 `snapshot` 不再被拒绝；带 `epoch` 的 `status` 正常返回；真正不合法的参数返回 HTTP 200 和 `INVALID_REQUEST`。
- 2,103 项 JVM 测试和 361 项 Node 测试（360 项通过，1 项为原有跳过）通过，lint 和 debug/AndroidTest 打包通过。
- 还没在真机上复测。

## Fixes

- **One extra field failed the whole call**: models often copy `epoch` from `status` into `snapshot`. The tool refused the call and the model only saw "HTTP 400". Copied context fields (`epoch`, `observationId`) are now ignored by actions that do not use them.
- **Readable refusals**: a genuinely invalid call returns HTTP 200 with `INVALID_REQUEST` and a fixed message listing each action's fields, instead of a bare HTTP 400. Nothing is executed.

## Verification scope

- On an API 35 / x86_64 emulator, against the real tool endpoint: `snapshot` with `epoch` is no longer refused, `status` with `epoch` succeeds, and an invalid field returns HTTP 200 + `INVALID_REQUEST`.
- 2,103 JVM and 361 Node tests (360 passed plus one existing skip) passed, with lint and debug/AndroidTest packaging.
- Not yet re-tested on a real phone.
